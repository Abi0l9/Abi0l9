# Portfolio evidence standards

This portfolio separates **publicly reviewable code** from **summaries of private product work**.

## Evidence labels

| Label | Meaning |
| --- | --- |
| **Public code** | The linked repository is visible for source inspection |
| **Repository-reviewed case study** | Technology and scope were checked against a private repository available to the author; underlying code remains private |
| **Product/UX case study** | Based on product requirements and work history, not necessarily a verified source audit |
| **Illustrative architecture** | A conceptual diagram of responsibilities, not an operational topology |

## Screenshots and demos

Only use real, current screenshots of an application that the author is permitted to show. Before publishing, remove or mask customer details, private admin information, API keys, access tokens, emails, session data, internal URLs, and unpublished business figures.

A screenshot is a visual sample, not proof of production traffic, uptime, correctness, or security.

When publicly available demonstrations have been independently checked and authorized for sharing, they can be added to the relevant case study with the date checked.

## Claims we intentionally avoid without evidence

- Unverified user counts, revenue, conversion uplift, and response-time improvements
- Unsupported claims that a solution is fully secure, accessible, or production hardened
- Implied source-code access to private repositories
- Claims of comprehensive test coverage without a test report
- Suggesting a technology is implemented solely because it appears in a dependency list

## What a reviewer can ask about

System boundaries, component choices, product decisions, trade-offs, tests, deployment processes, debugging, and maintenance responsibilities can be discussed without disclosing confidential information.
